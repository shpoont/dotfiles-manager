# Harbor agent tests for dotfiles-manager v2

This directory contains the local-private Harbor agent-evaluation suite for
`dotfiles-manager` v2 release-readiness questions that are judgment-heavy:
issue quality, happy-path user experience, recipe explanation clarity, and
native import/export safety review.

Harbor is **not** runtime product behavior. The `dotfiles-manager` CLI must
not depend on Harbor, RewardKit, Codex auth, Docker, or these eval files.
These cases complement normal Go unit, integration, contract, fixture,
snapshot, safety, and performance tests; they do not replace them.

## Local-private boundary

The suite is local-private by default:

- do not commit generated jobs, aggregate jobs, results, dashboards, raw
  transcripts, copied Codex auth, local Docker build contexts, or local
  output artifacts;
- keep copied Codex auth out of Docker build contexts and images; each
  case has a per-case `environment/.dockerignore`, Dockerfiles must
  not `COPY` or reference `auth.json`, and verifier auth is exposed only
  through a local-private read-only runtime source mount;
- the verifier copies that runtime-mounted auth source into a container-local
  temporary `CODEX_HOME` because Codex writes local helper state while
  starting; the temporary verifier home is removed by the case script and
  is never part of the Docker build context or image;
- `environment/codex-auth/config.toml` is generated by the local prepare
  script and ignored together with `auth.json`; committed
  `config.example.toml` and `README.md` files document the non-secret defaults
  and local-only auth handling without being mutated by Harbor runs;
- do not run the suite in CI, a cloud runner, or a shared environment until
  a separate auth and data-handling design is reviewed;
- do not use Harbor results as proof that deterministic CLI behavior works;
- failing Harbor cases should map back to product/spec gaps, issue-quality
  gaps, or reviewer judgment gaps.

Ignored local paths are defined in the repository `.gitignore`, including
`evals/harbor/jobs/`, `evals/harbor/all-jobs/`, `evals/harbor/results/`,
`evals/harbor/tmp/`, `evals/harbor/local-auth/`, `evals/harbor/local-build/`,
and `evals/harbor/local-output/`.

## Cases

| Case | Purpose |
| --- | --- |
| `issue-quality-v2-specs` | Check whether agent-authored v2 implementation issues are scoped, spec-referenced, safety-aware, and independent of v1 work. |
| `happy-path-ux-v2-cli` | Check whether the normal user flow for `init`, `add`, `status`, `diff`, `save`, and `apply` is explained simply while preserving safety boundaries. |
| `recipe-explain-clarity` | Check whether recipe/support explanations cover scopes, named locations, managed vs unmanaged values, optional groups, lifecycle, and redaction without live reads. |
| `native-safety-review` | Check whether native export/import proposals fail closed around arbitrary commands, secrets, opaque payloads, lifecycle, trust, backup, and verification. |

## Deterministic local validation

Run the committed structure/sample validation without Harbor auth, Docker,
GitHub writes, or network access:

```bash
evals/harbor/validate.sh
```

The validator checks every case has the required Harbor files, each case
README contains the required risk/spec/out-of-scope mapping, each objective
script is syntactically valid, each objective passes the committed sanitized
`fixture/sample-pass.md`, and each objective fails the committed
`fixture/sample-fail.md`. It also fails when local-private/generated Harbor
artifacts such as copied `auth.json`, `.harbor-auth-prepared`, `jobs/`,
`all-jobs/`, `results/`, dashboards, transcripts, JSONL logs, or generated
`environment/codex-auth/config.toml` files are present under `evals/harbor/`;
clean those before validation and before committing.

## Harbor preflight and execution

Use the local skill scripts when Harbor is installed and local-private auth
is intentionally available. From the repository root:

```bash
$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/preflight.py \
  --root "$PWD" \
  --case issue-quality-v2-specs
```

Run one case:

```bash
$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/run_case.py \
  --root "$PWD" \
  --case issue-quality-v2-specs
```

Run all cases:

```bash
$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/run_all.py \
  --root "$PWD"
```

View the dashboard/report locally:

```bash
$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/view_jobs.py \
  --root "$PWD" \
  --port 8080

$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/summarize_results.py \
  --root "$PWD"
```

Dashboard and summary artifacts are generated under ignored local Harbor
paths. If a case fails, record the product/spec gap or issue-quality gap in
the relevant GitHub issue or PR; do not commit raw transcripts or local
dashboard output. After any Harbor run, remove copied auth and local result
folders before running the strict validator or committing:

```bash
$HOME/.asdf/shims/python /Users/shpoont/.codex/skills/harbor-agent-tests/scripts/cleanup_auth.py \
  --root "$PWD" \
  --remove-config
rm -rf evals/harbor/jobs evals/harbor/all-jobs evals/harbor/results evals/harbor/dashboard
```

## Release-readiness role

Before a v2 release candidate, use these cases as a reviewer aid for:

- agent-generated issue quality;
- end-user convenience and safety communication;
- recipe/support explanation clarity;
- native export/import safety judgment.

A passing Harbor run is useful evidence for the human release review, but it
is not sufficient without the deterministic gates in
`docs/internal/specs/v2/11-mvp-acceptance-tests.md`.
